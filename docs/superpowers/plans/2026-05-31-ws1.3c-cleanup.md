### Task 2: Harden `topicsRepo.create` — UNIQUE(srs_cards.topic_id) + onConflict

**Background:** `topicsRepo.create` guards against a duplicate card by checking the in-memory store (`get(srsCards).find(c => c.topicId === topic.id)`). That guard misses cross-device / cold-store races: two clients could each insert a card for the same topic. A DB-level `UNIQUE(topic_id)` makes "one card per topic" an invariant; `onConflict: 'topic_id'` makes the auth upsert idempotent instead of erroring on a race.

**Files:**
- Migration: apply via Supabase MCP `apply_migration` (project `bzcanpehaoeminjbzpvq`)
- Modify: `src/lib/data/entities.ts` — the auth branch of `topicsRepo.create` (the `supabase.from('srs_cards').upsert(...)` call, ~line 153)

- [ ] **Step 1: Re-confirm no duplicates exist (migration would fail otherwise)**

Run this SQL via Supabase MCP `execute_sql` (project `bzcanpehaoeminjbzpvq`):
```sql
SELECT topic_id, COUNT(*) AS n FROM srs_cards GROUP BY topic_id HAVING COUNT(*) > 1;
```
Expected: empty result. If any rows return, STOP and dedup first (delete all but the most-recent card per `topic_id`) — do not apply the constraint over dupes.

- [ ] **Step 2: Apply the migration**

Use Supabase MCP `apply_migration` (project `bzcanpehaoeminjbzpvq`), name `add_unique_srs_cards_topic_id`:
```sql
ALTER TABLE public.srs_cards
  ADD CONSTRAINT srs_cards_topic_id_key UNIQUE (topic_id);
```

- [ ] **Step 3: Verify the constraint landed**

Run via `execute_sql`:
```sql
SELECT conname FROM pg_constraint
WHERE conrelid = 'public.srs_cards'::regclass AND contype = 'u';
```
Expected: one row, `srs_cards_topic_id_key`.

- [ ] **Step 4: Make the auth card upsert idempotent on topic_id**

In `src/lib/data/entities.ts`, inside `topicsRepo.create`, change the card insert from:
```ts
          const { error: ce } = await supabase.from('srs_cards').upsert(cardToRow(card));
          if (ce) throw ce;
```
to:
```ts
          const { error: ce } = await supabase
            .from('srs_cards')
            .upsert(cardToRow(card), { onConflict: 'topic_id' });
          if (ce) throw ce;
```
(`cardToRow` already emits `topic_id`; no other change needed.)

- [ ] **Step 5: Verify**

Run: `npm run check:all`
Expected: green.

- [ ] **Step 6: Commit**

```bash
git add -A
git commit -m "feat: UNIQUE(srs_cards.topic_id) + onConflict harden topicsRepo.create against duplicate cards"
```

### Task 3: Fix AI-suggested slots owned by `''` (RLS-hidden for auth users)

**Background:** `generateSchedule` builds suggested slots with `userId: ''` (it's a pure function with no auth context — see `src/lib/scheduler.ts` ~lines 193, 230). In guest mode that's harmless (localStorage ignores ownership). But when an authenticated user **accepts** a suggested slot, it's persisted with `user_id = ''`, which the RLS policy (`auth.uid() = user_id`) then hides — the slot silently vanishes on reload. Fix: stamp the real `userId` onto suggested slots the moment they enter the page store, in `handleAutoSchedule`. (`getAuthContext` is already imported and used elsewhere in this file, e.g. `handleCreateSlot`.)

**Files:**
- Modify: `src/routes/(app)/schedule/+page.svelte` — `handleAutoSchedule` (~lines 54–76)

- [ ] **Step 1: Inject userId onto suggested slots**

In `handleAutoSchedule`, change:
```ts
    const suggested = generateSchedule({
      weekStart: viewedWeekStart,
      subjects: $subjects,
      topics: $topics,
      sessions: $sessions,
      srsCards: $srsCards,
      tasks: $tasks,
      existingSlots: filteredSlots,
      settings: $settings,
      examDate: $settings.examDate,
    });
    scheduleSlots.update(all => [...all, ...suggested]);
```
to:
```ts
    const { userId } = getAuthContext();
    const suggested = generateSchedule({
      weekStart: viewedWeekStart,
      subjects: $subjects,
      topics: $topics,
      sessions: $sessions,
      srsCards: $srsCards,
      tasks: $tasks,
      existingSlots: filteredSlots,
      settings: $settings,
      examDate: $settings.examDate,
    }).map(s => ({ ...s, userId }));
    scheduleSlots.update(all => [...all, ...suggested]);
```

- [ ] **Step 2: Verify**

Run: `npm run check:all`

### Task 5: Fix `/schedule` SSR 500 — `document` in `WeekGrid.onDestroy`

**Background:** Hard-loading `/schedule` (refresh or direct URL) 500s. During SSR, SvelteKit renders the component then destroys it, so `onDestroy` runs **on the server**, where `document` is undefined → ReferenceError. In `src/lib/components/calendar/WeekGrid.svelte`, `onDestroy` (~lines 440–447) calls `document.removeEventListener(...)`. `clearInterval`/`clearHoldTimer` are server-safe; only the `document.*` calls must be guarded. Use SvelteKit's `browser` flag. (`onMount` is fine — it never runs on the server.)

**Files:**
- Modify: `src/lib/components/calendar/WeekGrid.svelte` — imports + `onDestroy` (~lines 1–10 and 440–447)

- [ ] **Step 1: Import the `browser` flag**

Add to the component's `<script>` imports (near the other `$app`/`svelte` imports at the top):
```ts
  import { browser } from '$app/environment';
```

- [ ] **Step 2: Guard the document calls in `onDestroy`**

Change:
```ts
  onDestroy(() => {
    clearInterval(nowInterval);
    clearHoldTimer();
    document.removeEventListener('mousemove', onMousemove);
    document.removeEventListener('mouseup', onMouseup);
    document.removeEventListener('touchmove', onTouchmove);
    document.removeEventListener('touchend', onTouchend);
  });
```
to:
```ts
  onDestroy(() => {
    clearInterval(nowInterval);
    clearHoldTimer();
    if (!browser) return;
    document.removeEventListener('mousemove', onMousemove);
    document.removeEventListener('mouseup', onMouseup);
    document.removeEventListener('touchmove', onTouchmove);
    document.removeEventListener('touchend', onTouchend);
  });
```

- [ ] **Step 3: Verify build + types**

Run: `npm run check:all`
Expected: green.

- [ ] **Step 4: Browser-verify the exact repro**

Expected: page renders, no 500, no SSR error in the terminal.
